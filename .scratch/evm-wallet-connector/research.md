# EVM wallet connector API research

Checked and revised 2026-08-23 after live wallet validation. This is a provider and privacy review for a connector that accepts one EVM address and returns native balances, fungible tokens, and NFTs across Ethereum-compatible networks. DeFi positions are explicitly treated as a later enhancement.

## Decision in one paragraph

Do not use Routescan or Blockscout as the source of truth for a complete portfolio: both failed the user's real-wallet coverage test. No reviewed hosted API is simultaneously keyless, durably free, privacy-maximal, and complete enough to match a modern wallet. The simplest credible V1 is Zerion's indexed wallet positions API behind a small Satella-operated, no-log relay. The user supplies only an address, the relay injects an operator credential, and results preserve chain, asset, protocol, and position type. Zerion can return direct wallet assets and decoded DeFi positions through the same paginated endpoint. Its free Developer plan can fund a prototype, not an unlimited production product.

A relay is a deliberate change from Satella's current local-only architecture. It hides the user's IP from the portfolio provider, but the relay can observe the IP/address pair unless it is designed not to retain it. It must disable request logging and analytics, redact addresses from errors, strip forwarding headers upstream, and use only bounded memory caching. The strongest privacy architecture remains self-hosted indexing and RPC, but that is substantially more infrastructure and does not make raw JSON-RPC a wallet portfolio API.

Routescan is rejected as the primary despite attractive documentation. The user's live wallet test showed that its advertised cross-chain `all` query missed assets on Arbitrum, Optimism, and Base. A 200 response is not enough when holdings are incomplete, so Routescan is disqualified for this connector unless a future implementation proves the provider's coverage with a real-wallet regression suite: [Routescan plans](https://routescan.io/docs/plans-and-limits/api-keys-and-pricing), [Routescan address API](https://routescan.io/docs/api/addresses).

## What “all holdings” can and cannot mean

An EVM address is the same identifier across chains, but there is no chain-level JSON-RPC method called “list every asset owned by this address.” Ethereum's official JSON-RPC API exposes state and history methods such as `eth_getBalance`, `eth_getLogs`, and `eth_call`, each against a particular node and chain: [Ethereum JSON-RPC API](https://ethereum.org/developers/docs/apis/json-rpc/) and [EIP-1474](https://eips.ethereum.org/EIPS/eip-1474). A caller can invoke `balanceOf(address)` once it already knows a token contract. It cannot discover every token contract, NFT collection, or protocol position from those methods alone.

Multicall3 reduces the number of RPC round trips, but it does not change that limitation. The official contract aggregates caller-supplied calls and returns their results; it has no index of token contracts or wallets: [Multicall3 source](https://github.com/mds1/multicall3/blob/main/src/Multicall3.sol). A direct-RPC implementation therefore needs a maintained token list per chain, event scanning, or its own indexer. DeFi positions need protocol-specific decoding because the wallet may own a receipt token, an LP position, or a claim in a contract rather than a plain ERC-20 balance.

“All chains” should mean “all supported and indexed chains in the selected provider,” with the connector reporting the provider's last indexed block and any unavailable chains. No reviewed hosted provider covers every current or future EVM chain with identical data quality.

## Privacy model

The address and its on-chain activity are public. The privacy-sensitive association is which person, IP address, or app session queried it and when.

| Request path                                    | Provider can associate                                                                                                           | Satella can associate                                                                | Main tradeoff                                                                |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Client directly to a keyless API                | Address in the URL/body, IP, user agent, timing, and response behavior                                                           | The local UI can know the address; no Satella server request is needed               | No operator proxy, but the indexer sees the user's network identity.         |
| Satella proxy to a hosted API                   | Address and Satella server IP, timing, and any operator key                                                                      | User account/session and address unless deliberately separated and logs are disabled | Hides the user's IP from the provider, but makes Satella a trusted link.     |
| User-selected proxy or Tor/VPN to a keyless API | Proxy/provider sees the query; identity linkage depends on the proxy                                                             | Satella may see only local state if no telemetry is sent                             | More private, but adds UX and abuse/rate-limit complexity.                   |
| Self-hosted indexer and nodes                   | No hosted portfolio vendor needs to receive each lookup; node peers and any bootstrap/RPC dependencies still see network traffic | The operator controls the database, logs, and address-to-user linkage                | Best control, highest operating cost, and significant indexing work.         |
| Public JSON-RPC directly                        | RPC provider sees each request and the queried address/contract targets                                                          | Usually no server-side portfolio record                                              | Cheap and private only relative to Satella; it still lacks wallet discovery. |

There is no single privacy policy covering every public Blockscout instance. Blockscout's current hosted-service notice lists wallet addresses, wallet balances, transactions, IP address, device details, and product-usage data; it says wallet data is retained while a wallet remains connected and usage data may be retained while the product is used and for seven years thereafter when identifiable: [Blockscout privacy notice](https://eaas.blockscout.com/privacy-notice). Self-hosted and partner-operated instances can have different policies. Therefore "keyless" means no credential or account, not no logging. For the federation path, avoid putting the address in Satella telemetry, redact provider URLs from logs and errors, and make the per-instance provider choice explicit in the product's privacy copy.

Do not expose an operator API key in a browser bundle. Any key-bearing provider should be called from a proxy or from a local engine that keeps the key outside web-visible code. A proxy should use bounded rate limits, no request-body or URL logging, short-lived in-memory caching if needed, and no analytics on address values.

## Keyless alternatives checked

No stronger true keyless aggregator survived both the credential and coverage tests. Ankr's Advanced API documents an API-key URL and a live empty-key request returned HTTP 403; the demo key shown in documentation is not a shippable public credential: [Ankr API reference](https://www.ankr.com/docs/api-reference/), [Advanced API](https://www.ankr.com/web3-api/advanced-api/). GoldRush x402 can avoid an account/API key, but it is pay-per-request, not free for production: [GoldRush x402](https://goldrush.dev/docs/goldrush-x402/overview). The Graph, Alchemy, Moralis, Zerion, Covalent/GoldRush foundational API, DeBank, and Zapper all require a key or paid account for the relevant wallet APIs. Direct JSON-RPC and Multicall3 remain keyless low-level primitives, but cannot discover every token/NFT contract or protocol position. Blockscout federation was the only plausible no-account path, but the real-wallet miss means it is not acceptable as a complete holdings source either.

## How Rabby and MetaMask achieve better coverage

They use subsidized first-party indexing services, not plain public RPC discovery. Rabby's published client calls wallet-specific `api.rabby.io` routes for token lists, total balances, NFTs, and simple/complex protocol positions: [official Rabby API client](https://github.com/RabbyHub/rabby-api). Requests are signed by Rabby's WebAssembly signer and the package is marked `UNLICENSED`; this is observable first-party client code, not a stable public API contract Satella can responsibly reuse without permission. Its rich protocol responses explain why Rabby can normalize bridged assets and decode lending, LP, staking, borrow, reward, and collateral positions.

MetaMask likewise calls its own Accounts, Portfolio, Token, NFT, Price, and DeFi-adapter services in addition to Infura RPC. The official extension's network inventory includes `accounts.api.cx.metamask.io`, `portfolio.api.cx.metamask.io`, `token.api.cx.metamask.io`, `nft.api.cx.metamask.io`, `price.api.cx.metamask.io`, and `defiadapters.api.cx.metamask.io`: [MetaMask privacy snapshot](https://github.com/MetaMask/metamask-extension/blob/main/privacy-snapshot.json). MetaMask Mobile's public build configuration points to the same Portfolio service: [mobile build configuration](https://github.com/MetaMask/metamask-mobile/blob/main/builds.yml). These endpoints are implementation dependencies of MetaMask products, not documented public Portfolio APIs for third-party applications.

## Scraping the public Zerion portfolio page

Do not ship `app.zerion.io/{wallet}/overview` scraping as a connector without Zerion's written permission. Zerion's current API agreement expressly prohibits scraping the service, requires customer applications to use published API methods, and prohibits replacing API calls with non-API calls to work around API limitations: [Zerion API agreement, sections 1.6–1.7](https://www.zerion.io/api-license-agreement). The general web-app terms also prohibit abusive activity that imposes disproportionate infrastructure load: [Zerion terms](https://www.zerion.io/terms-conditions). A scraper framework does not change this provider-specific constraint.

The technical path is also weaker than the API. The portfolio is a JavaScript application whose DOM, labels, pagination, lazy loading, experiment flags, bot controls, and aggregation views are not a data contract. Scraping visible rows risks rounded quantities, missing off-screen positions, loss of chain/contract identifiers, and silent breakage after a UI release. It sends more browser telemetry and third-party requests than the narrow API path, so it is not a privacy improvement. At most, treat it as a manual diagnostic tool for comparing provider coverage, never an automatic 15-minute production source.

Zerion now offers a legitimate no-key alternative through x402: each API request can be paid in USDC on Base without a subscription or API key. The published example price is $0.01 per request: [Zerion x402 announcement](https://zerion.io/blog/zerion-api-supports-x402/). This is permissionless and structured, but not free; at a 15-minute cadence it would cost about $28.80 per single-page wallet per month before pagination or retries.

For each instance, the no-key V2 calls are:

1. `GET /api/v2/addresses/{address}` for native balance. The response includes `coin_balance`, `exchange_rate`, and `block_number_balance_updated_at`: [address info](https://docs.blockscout.com/api-reference/get-address-info).
2. `GET /api/v2/addresses/{address}/tokens?type=ERC-20` for fungible holdings. The endpoint returns `items` and `next_page_params`, and the `type` filter supports ERC-20, ERC-721, and ERC-1155: [filtered token balances](https://docs.blockscout.com/api-reference/token-balances-with-filtering-and-pagination).
3. `GET /api/v2/addresses/{address}/nft?type=ERC-721,ERC-1155` for NFT instances. The response is paginated with `items` and `next_page_params`: [NFT holdings](https://docs.blockscout.com/api-reference/get-list-of-nft-owned-by-address).

The documented `token-balances` endpoint returns an array and is not paginated. It is useful for probing but can be very large and can time out for a whale address. Use the filtered `/tokens` endpoint with cursor pagination in the connector. A live no-auth probe on 2026-08-23 against a public active address returned HTTP 200 JSON for address info and token balances on Ethereum, Arbitrum One, OP Mainnet, Base, Polygon, Gnosis, Scroll, ZKsync, Mode, Celo, Arbitrum Nova, and several additional registry instances. The probe is evidence that the routes are currently reachable, not a guarantee of complete holdings for every address. The user's actual wallet test is the stronger acceptance criterion: it showed Routescan missing Arbitrum, Optimism, and Base assets, while Blockscout returned current native and ERC-20 data on those chains.

There are two rate/deprecation caveats. Blockscout's current request-limit page says no-key per-instance access is being deprecated “July 1” in favor of PRO and lists a no-key value of 3 in the requests/second column, while its description also says a default of 300 requests/minute. A live response exposed an `x-ratelimit-limit` of 180 on tested hosts. Treat these as instance/configuration-dependent rather than a stable contract: use sequential bounded requests, back off on 429, and expose per-chain errors. The PRO API's free plan advertises 5 RPS and 100,000 credits/day, but it needs an operator account/key: [requests and limits](https://docs.blockscout.com/devs/apis/requests-and-limits), [PRO API](https://docs.blockscout.com/devs/pro-api). Satella cannot ship that shared secret in a packaged desktop.

Hosted Blockscout instances are not one privacy domain. The API address path sends the wallet to each instance, and the Blockscout hosted privacy notice describes wallet addresses/balances, IP/device data, usage analytics, and retention while connected. Partner and self-hosted instances may have different policies: [Blockscout privacy notice](https://eaas.blockscout.com/privacy-notice). A direct desktop federation is therefore keyless and avoids a Satella backend, but it leaks the user's IP and address to multiple operators. A user-controlled VPN/Tor/proxy is the only way to change that without adding a Satella server.

## Recommended V1 shape

Keep the provider behind a Satella-owned interface and call Zerion's paginated `/v1/wallets/{address}/positions/` operation through a minimal relay. V1 should:

- accept one checksummed or lowercase `0x` address without resolving ENS;
- query the supported chains relevant to Satella and keep Zerion's chain relationship on every result;
- start with `filter[positions]=only_simple`, then enable `no_filter` or a separate slower `only_complex` refresh after the domain mapping is verified;
- request EUR-denominated values and follow every `links.next` cursor;
- preserve chain, fungible identity, protocol, group, and position type on every result rather than deduplicating by symbol;
- create one wallet account per chain under one EVM-wallet custodian, so chain provenance is never lost;
- mark an unavailable or truncated provider response as a refresh error, never as a zero balance;
- keep the Zerion credential only on the relay; never embed it in the desktop package;
- disable relay request logging and analytics, redact addresses from errors, strip forwarding headers upstream, and cache only in bounded memory;
- avoid fetching arbitrary token-supplied image URLs; use provider-cached media or a controlled allow-list;
- validate coverage with representative real wallets, including the user's Base wstETH holding, and pin pagination, partial-failure, spam-token, and zero-balance behavior in integration tests.

Do not add DeFi positions to this first connector. A wallet can have valuable exposure represented by lending receipts, LP positions, vault shares, staking contracts, vesting claims, and protocol-specific NFTs. A raw ERC-20/NFT list would either omit those positions or double-count their underlying assets. A later provider enrichment can expose those as a separate “protocol positions” section, with source and confidence, rather than folding them into simple wallet balances.

## V2 and self-host options

DeBank Cloud is the closest alternative and likely the best benchmark for Rabby-like coverage. Its official Pro API exposes all-chain token and complex-protocol routes and requires an `AccessKey`; usage is sold in compute units at a published base price of 1 million units per 200 USDC: [DeBank user API](https://docs.cloud.debank.com/en/readme/api-pro-reference/user), [DeBank pricing](https://open.debank.com/). It is not a durable free path. Alchemy remains a simpler fungible-token fallback if Zerion's terms, quota, or coverage do not pass acceptance testing.

If maximal privacy is more important than time-to-market, run a local or operator-controlled index. Blockscout is the most directly relevant open-source explorer stack, but operating a complete explorer per chain is heavy. Envio HyperIndex or Subsquid can produce a narrower local dataset, but they require engineering an event/indexing model, token/NFT metadata handling, reorg recovery, and chain infrastructure. The Graph Node is another self-hostable option, though generic subgraphs are not a universal portfolio index and still require a custom schema and mappings.

## Bottom line

No single reviewed hosted API is both keyless and reliable across the user's tested major chains. Routescan and Blockscout both failed the real-wallet coverage test. The simplest defensible prototype is Zerion's positions API behind a deliberately privacy-limited Satella relay, with direct wallet positions first and decoded DeFi enabled once Satella can represent it without double-counting. DeBank Cloud is the strongest second implementation to benchmark, not the free choice. Direct JSON-RPC is more primitive, not more complete. Self-hosting is more private, not simpler.
